# Describe-a-loop eval

Example sentences for the describe-a-loop feature, with the answers it should give. A language model is right most
of the time rather than always, so it gets a score over many examples instead of a pass or fail per example.

The cases are hand-written, never generated by the model being tested.

## `cases.json`

**Profiles** are the options a person has. Every person has the app's starter options, which aren't copied here:
the eval reads them from the app's code, so a starter that's renamed or added reaches the eval without editing this
file. A profile's `added` lists only the options the person made themselves, by id and label, on top of the
starters. `startersOnly` has none added; `custom` adds a few.

**A case** has:

- `id`, `kind` (what it tests) and `text`, the sentence as typed or dictated.
- `split`: `practice` cases are used while tuning the instructions; `final` cases are kept back for the honest score.
  Don't tune against the final set, or the score measures memory rather than how the feature handles new sentences.
- `profile`: which options the person has.
- `expect`: for each step, the answers counted as right. An option id, such as `trigger.work` or `custom.exams`,
  or `none` when the step should be left empty because the sentence doesn't say. `result.notSure` is different
  from `none`: it's the "Not sure" option, for when the person says they couldn't tell.
- `newOptions` (optional): when none of the person's options fit, the feature suggests a new one in their own words,
  such as "+ Landlord". This field says which steps should get such a suggestion. See below.
- `note` (optional): why the expected answer is what it is.

### New-option suggestions

Take "My landlord texted again and I kept checking my phone." No trigger fits, so the trigger step should get a
suggestion. The case says so like this:

```json
"newOptions": { "trigger": { "accept": ["landlord"], "required": true } }
```

- **Which step:** the key, here `trigger`. Only the steps listed may get a suggestion. A suggestion for any other step
  counts as a mistake: in this case, suggesting a new behavior would be wrong, because Kept checking fits.
- **What the label should be:** `accept` lists words, and the suggested label is right if it contains any one of
  them, ignoring case. "Landlord" and "Landlord texts" both count; "Rent" doesn't.
- **Whether it must appear:** `required: true` means leaving the suggestion out counts against the score.
  `required: false` means a suggestion is welcome but not expected, for sentences where an existing option also
  fits. In "Job interview tomorrow…", Work fits, so suggesting "Interview" is fine and so is not suggesting it.

A case without `newOptions` must get no suggestion for any step.

## Scoring

For each step, a model answer is one of:

- **right**: one of the expected answers.
- **not sure**: left empty when an option was expected. A small cost: the person taps it themselves.
- **wrong**: an option that isn't expected. The real failure: the person has to notice it and change it.

New-option suggestions are scored separately: suggested when required, not suggested when a step isn't listed, and
the label containing one of the accepted words.

The bar to ship, on the final set: at least 85% right per step, no more than 5% wrong, new options suggested for
most required cases and almost never when an existing option fits, and under about 2 seconds per sentence.

## Reusing the final set

Run the final set as often as you like to check nothing got worse: after an iOS update changes the model, after
editing the instructions, before each release. Running it doesn't spoil it. Letting it steer changes does:

- Make every decision with the practice set: read its failures, try changes, compare scores.
- Run the final set at milestones, such as "is this ready to ship?", and treat its score as a report. Don't keep
  whichever version of the instructions scores best on it.
- When a final case fails, look at it to understand why, then write a new, similar practice case and tune against
  that, not the final case itself.

Refresh the final set once it has been consulted many times or its failures studied closely, or when people start
using the feature in ways it doesn't cover: move its cases into practice and write new final ones.

## Running it

The `LooseningWorryEvals` scheme runs the cases through the Evaluations framework against Apple's Private Cloud
Compute model, which the logger reads with first. Add `TEST_RUNNER_EVAL_MODEL=onDevice` before `xcodebuild` to score
the on-device model instead, which reads when the cloud can't, such as offline. Each is scored alone, never falling
back, so the score says which model answered.

Run it on an iPhone with Apple Intelligence on, unlocked: the simulator's on-device model is far slower and its
timings mean nothing. The cloud model needs the app's Private Cloud Compute entitlement, which `project.yml` sets.

```bash
xcodebuild test -project LooseningWorry.xcodeproj -scheme LooseningWorryEvals \
  -destination 'platform=iOS,id=<iPhone UDID>' -allowProvisioningUpdates -collect-test-diagnostics never
```

Only the practice set runs. Add `TEST_RUNNER_EVAL_FINAL=1` before `xcodebuild` to run the final set too. The test
fails until the ship bar is met; the console prints each score, and Xcode's test report has the Evaluations report
with every sentence, what was read, and why it scored as it did. A sentence the model refuses, or its guardrails
stop, reads as nothing, as it does in the app.

## Adding cases

Add a case when a real sentence goes wrong, from testing or from beta testers who agree to share it with names and
details removed. New cases go in `practice` unless the final set is being refreshed as a whole.
